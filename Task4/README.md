# Проектирование продажи ОСАГО

Наблюдения:
1. > Бизнесу важно, чтобы на экране пользователя предложения от каждой страховой
  компании отображались сразу, как только от неё пришёл ответ

   В этом случае нужно использовать `server push`. В теории у нас тут два
   варианта: `Long polling` и `WebSocket`.
  
   Но кажется, что первый вариант сложнее в реализации, так как инстансов
   `core-app` может быть несколько. При этом каждый запрос `Long polling`'а может
   попадать на разные сервера, из-за чего придется думать о сохранении данных в
   БД, чтобы любой сервер мог их читать. Ну или нужно использовать
   `sticky sessions`, чего тоже не хочется.

   Соответственно, выбор пал на `WebSocket`, который нужно поддержать в
   `core-app`.

2. В случае с веб-сокетами, чтобы не нагружать систему постоянными запросами
   от `core-app` к `osago-aggregator`, нужно предоставить асинхронное API.
   В результате, `core-app` будет отправлять запрос с заявкой, а
   `osage-aggregator` будет отправлять HTTP-запросы в страховые компании и,
   получив ответ, пушить его в очередь событий.

3. > Максимальное время ожидания решения от страховой компании — 60 секунд
    
   Чтобы это поддержать, необходимо настроить таймауты для запросов из
   `osago-aggregator` в страховые компании. Причем желательно добавить ретраи,
   а ограничение по времени поставить суммарное на все попытки запросов.

   Условно, сервис будет пытаться получить предложение от страховой компании
   5 раз, суммарно не дольше 60 секунд.

4. API страховых компаний, как и любые внешние системы, могут быть недоступны
   продолжительное время. Чтобы не увеличивать нагрузку и не заваливать упавшие
   системы кучей ретраев, желательно настроить на этих интеграциях
   `Circuit Breaker`.

5. При работе с веб-сокетами важно, чтобы сообщение от `osago-aggregator` из
   очереди событий получил конкретный экземпляр сервиса `core-app`, который
   поддерживает соединение с пользователем (через gateway, конечно).

   Для этого будем выделять консьюмеров на каждом экземпляре `core-app` в
   отдельную `consumer group`. Тогда каждый инстанс будет читать все события
   в очереди, но потом фильтровать только те из них, которые относятся к
   обрабатываемым этим инстансом веб-сокетам.

6. В такой реализации отдельное хранилище данных для `osago-aggregator` не нужно,
   так как по сути хранить входящие и исходящие запросы будет очередь событий.
